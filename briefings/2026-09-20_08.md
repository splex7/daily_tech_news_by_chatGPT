## 2. Plugin4Shell — Claude Code·Codex·Copilot·Gemini CLI의 Plugin Supply Chain을 동시에 찌른 Zero-click RCE

![AI coding agents](https://substackcdn.com/image/fetch/%24s_%21iJZC%21%2Cf_auto%2Cq_auto%3Agood%2Cfl_progressive%3Asteep/https%3A%2F%2Fsubstack-post-media.s3.amazonaws.com%2Fpublic%2Fimages%2F160cdc0f-548e-4942-b4a2-edbd2a571ec7_1536x1024.png)

### 핵심 요약

AIR Security가 `Plugin4Shell`이라는 Coding Agent 공급망 취약점을 공개했습니다. AIR의 분석에 따르면 Claude Code, OpenAI Codex, GitHub Copilot, Gemini CLI가 Plugin을 특정 Git Commit SHA에 고정할 때 **요청한 SHA와 실제 Checkout된 HEAD가 같은지 마지막에 검증하지 않는 설계 오류**를 공유했습니다.

공격자가 Plugin Repository를 장악하면 검토된 Plugin의 Pin 자체는 정상처럼 보이게 유지하면서 다른 코드를 실행하게 만들 수 있습니다. Claude Code와 Codex처럼 Plugin Auto-update가 켜져 있는 환경에서는 사용자의 추가 클릭 없이 기존 Plugin이 바뀔 수 있어 AIR는 이를 Zero-click RCE로 분류했습니다.

Anthropic은 Claude Code 2.1.179에서, OpenAI는 Codex 0.146.0에서 수정했습니다. GitHub는 GitHub.com이 40자리 Hex 형태의 Branch 이름을 막기 때문에 자사 Marketplace 경로에서는 AIR이 제시한 방식이 성립하지 않는다는 입장입니다. AIR은 Bitbucket이나 Self-hosted Git 등 Coding Agent가 공식적으로 지원하는 다른 Plugin Source까지 고려하면 Agent-side 검증이 필요하다고 반박합니다. Google은 기존 Gemini CLI를 Deprecated하고 Antigravity로 이동하도록 안내했습니다.

### 왜 중요한지

Agent 보안의 공격면이 **Prompt Injection → Tool Permission → Plugin·Skill Supply Chain**으로 빠르게 이동하고 있습니다.

Coding Agent Plugin은 일반 IDE Extension보다 위험할 수 있습니다. Agent가 가진 File, Shell, Git, Cloud Credential 권한을 그대로 물려받기 때문입니다. 앞으로 Agent 생태계에서 `Commit SHA를 Pin했다`만으로는 충분하지 않고 **Resolved HEAD Verification, Signed Artifact, Trusted Marketplace, Permission Isolation, Runtime Audit** 같은 소프트웨어 공급망 통제가 기본 요구사항이 될 가능성이 큽니다.

## 3. Cloudflare `security-audit-skill`, GitHub Trending 1위 — 보안 리뷰도 단일 Agent가 아니라 검증 Agent Loop로

![Cloudflare](https://miro.medium.com/v2/0%2AVkJT7OxqPFNNts18.png)

### 핵심 요약

Cloudflare의 MIT 오픈소스 `security-audit-skill`이 9월 19일 GitHub Trending 집계에서 **전체 1위**로 올라왔습니다. 기술 자체는 6월 공개됐지만 이번 주에 Stars가 폭발적으로 증가하며 다시 크게 주목받고 있습니다. GitHub Trending 추적 스냅샷에서는 9월 19일 기준 14K 이상의 Stars와 하루 수천 Stars 수준의 증가세가 관측됐습니다.

이 Skill은 Coding Agent에게 단순히 `코드에서 취약점을 찾아라`고 시키는 Prompt가 아닙니다. **Reconnaissance → Coverage-led Hunting → Candidate Validation → Structured Findings → Independent Record Verification → Report**의 6단계 Workflow를 정의합니다. 특히 취약점을 발견한 Agent와 이를 검증하는 Agent를 분리하고, `confirmed`, `needs_validation`, `rejected` 상태를 JSON Schema로 관리합니다.

Cloudflare는 Target Code를 실제 실행해야 할 경우 External Network 차단, Sanitized Environment, Read-only Target, Resource Limit을 갖춘 OS-level Sandbox를 요구합니다. 조건이 부족하면 Agent가 발견한 내용을 확정 취약점으로 올리지 않고 `needs_validation` 상태로 남기도록 설계했습니다.

### 왜 중요한지

이 프로젝트가 주목받는 이유는 Agent의 품질을 **더 좋은 Prompt 하나**가 아니라 **Workflow와 Verification Architecture**로 끌어올리는 방법을 잘 보여주기 때문입니다.

보안처럼 False Positive 비용이 큰 업무에서는 `Agent가 발견했다`가 끝이 아니라 **다른 Agent가 반박을 시도하고, 기계적으로 검증할 수 있는 Artifact를 남기며, 실행환경까지 격리하는 구조**가 필요합니다. Agent Skill이 단순 사용법 문서에서 점점 작은 `업무 프로그램`으로 발전하고 있다는 대표적인 사례입니다.

## 4. Linkup `SPARSEUP` — 149M Open Sparse Embedding Model, Dense Vector 일변도의 Retrieval에 다시 선택지

![Sparse retrieval model](https://image.vuukle.com/highres/image-quizzly.ai-08f683e1-a88f-4cc0-95c0-38d428576b54/5c4df86f599b7bc6feb0e50b4267a540)

### 핵심 요약

Linkup Research가 첫 오픈모델 `SPARSEUP`을 공개했습니다. **149M Parameter ModernBERT Backbone** 기반의 Learned Sparse Embedding Model이며 Apache 2.0으로 배포되고, Hugging Face Weight를 Transformers 또는 Sentence Transformers에서 사용할 수 있습니다. Linkup 홈페이지도 현재 `SPARSEUP is live`라고 공식적으로 안내하고 있습니다.

Linkup이 공개한 결과에서 SPARSEUP은 BEIR-13 평균 **56.4 nDCG@10**을 기록했습니다. Linkup은 이를 150M 미만의 공개 Vocabulary-based Sparse Encoder 가운데 가장 강한 결과라고 설명합니다. 다만 전체 Retrieval 방식끼리 비교하면 동일 계열의 DenseOn 57.9, LateOn 58.9보다 낮으므로 `전체 Embedding SOTA`로 해석하면 안 됩니다.

Sparse Embedding은 Dense Vector와 달리 실제 Vocabulary 차원에 Weight를 배치하므로 Inverted Index와 잘 맞고, 어떤 Token이 검색 결과에 기여했는지 해석하기 쉽습니다. SPARSEUP은 Vanilla SPLADE가 ModernBERT에서 지나치게 많은 Stopword를 활성화하는 문제를 줄이기 위해 Logit Shift, Token별 Top-k, Case Folding 등을 적용했습니다.

### 왜 중요한지

RAG와 Agent Search가 커질수록 Retrieval은 단순히 `Embedding API를 호출하고 Vector DB에 넣는다`로 끝나지 않습니다. 제품 검색, 법률, 코드, 기술문서처럼 **희귀 Keyword와 정확한 용어 Matching이 중요한 영역**에서는 Sparse Retrieval이 여전히 강점이 있습니다.

SPARSEUP은 `BM25 vs Dense Vector`라는 오래된 양자택일이 아니라 **Learned Sparse + Dense + Late Interaction을 함께 조합하는 Hybrid Retrieval**이 다시 중요해지고 있음을 보여줍니다. Agent 시대에는 Model뿐 아니라 Agent가 어떤 정보를 얼마나 정확하고 싸게 찾는지가 전체 성능을 크게 좌우합니다.

## 5. TencentCloud `Octop` GitHub 급부상 — Self-hosted Multi-Agent가 개인용 Chatbot에서 작은 Agent OS로

![Tencent Cloud multi-agent](https://developer.qcloudimg.com/http-save/yehe-11721088/a6ac004946442f3cba7b9b2932c83a89.png)

### 핵심 요약

TencentCloud의 MIT 오픈소스 `Octop`이 9월 19일 GitHub Trending 신규 진입 프로젝트 가운데 하나로 올라왔습니다. 확인 시점 GitHub에서 약 **4.1K Stars**를 기록하고 있으며, Self-hosted·Multi-user·Multi-agent Assistant를 지향합니다.

Octop은 Web Dashboard와 CLI뿐 아니라 Feishu, DingTalk, QQ, Discord, WeCom 같은 Messaging Channel을 하나의 Runtime에 연결합니다. 각 사용자는 별도 Agent·Workspace·Provider·Cron을 가질 수 있고, JWT Isolation, Tool Approval, Shell Guardrail, PII Redaction을 기본 기능으로 둡니다. OAuth와 MCP Connector, RAG Knowledge Base, Browser Automation, Terminal, Remote Desktop도 포함됩니다.

개발자 관점에서 흥미로운 부분은 ACP Agent Client Protocol을 양방향으로 지원한다는 점입니다. 외부 IDE가 Octop Agent를 호출할 수도 있고, 반대로 Octop이 OpenCode, CodeBuddy, Claude Code, Codex 같은 Coding Agent에 작업을 위임할 수도 있습니다. 기본 상태는 SQLite 또는 PostgreSQL에 보존되고 재시작 후에도 Agent Runtime을 복구하도록 설계됐습니다.

### 왜 중요한지

Self-hosted AI가 `Ollama로 로컬 모델 하나 실행` 수준에서 **Identity + Memory + Tools + Browser + Messaging + Scheduler + Multi-Agent Orchestration**을 묶는 개인·소규모 조직용 Control Plane으로 발전하고 있습니다.

Octop 같은 프로젝트가 성장하면 사용자는 특정 LLM 회사의 Chat UI가 아니라 **자신이 소유한 Agent Runtime에 여러 Model과 Tool을 꽂아 쓰는 구조**를 선택할 수 있습니다. Agent 생태계에서 장기적으로 중요한 경쟁축 중 하나가 `어떤 모델을 쓰는가`에서 `Agent의 상태와 데이터, 권한을 누가 소유하는가`로 이동할 수 있음을 보여주는 흐름입니다.

## 이번 회차의 핵심

이번 다섯 소식은 **Frontier Model → Agent Supply Chain → Verified Skill Workflow → Retrieval Infrastructure → Self-hosted Agent Runtime**으로 이어집니다.

Anthropic 사례는 모델 경쟁이 여전히 빠르게 진행 중임을 보여주지만, 나머지 네 소식은 실제 Agent 경쟁력이 이미 모델 바깥으로 크게 확장됐음을 보여줍니다. Plugin4Shell은 Agent Plugin의 공급망을, Cloudflare Skill은 검증 가능한 Agent Workflow를, SPARSEUP은 Agent가 정보를 가져오는 Retrieval Layer를, Octop은 사용자가 직접 소유하는 Agent Control Plane을 각각 보여줍니다.

> 앞으로의 Agent Stack은 **Model + Retrieval + Skill + Plugin Supply Chain + Runtime + Identity + Verification** 전체를 함께 설계해야 합니다.
