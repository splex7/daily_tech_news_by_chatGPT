## 1. GitHub Agentic Workflows `v0.88.4` — Agent를 GitHub Actions에 넣되, 네트워크·데이터 흐름까지 정책으로 통제

![GitHub Agentic Workflows](https://opengraph.githubassets.com/1/github/gh-aw)

### 핵심 요약

GitHub가 9월 7일 `github/gh-aw` 주간 업데이트와 `v0.88.4`를 공개했다. GitHub Agentic Workflows는 자연어 Markdown으로 Agent Workflow를 작성한 뒤 GitHub Actions로 컴파일해 실행하는 오픈소스 프로젝트다. Copilot, Claude Code, Codex, Gemini 등을 Agent Runtime으로 사용할 수 있다.

이번 릴리스의 중심은 **Agentic Firewall과 CI 신뢰성 강화**다. Trusted Enclave Workflow에 더 세밀한 sensitivity 제어를 추가했고, GitHub App 인증 Workflow에서는 DIFC 기반 데이터 흐름 무결성·기밀성 정책을 자동 생성하도록 했다. 최근 PR들도 Sandbox, Model Configuration, Safe Output 처리와 네트워크 계층을 강화하는 데 집중됐다.

GitHub의 보안 아키텍처는 Agent를 격리된 실행환경에 넣고 HTTP·HTTPS 트래픽을 Agent Workflow Firewall을 통해 Domain Allowlist로 제한한다. API Key도 Agent Process에 직접 주지 않고 별도 Proxy 계층에 둘 수 있다.

### 왜 중요한가

Agent를 CI/CD에 넣으면 생산성은 높아지지만, Repository Code·Secret·Network·Write Permission에 동시에 접근하게 된다. 기존 GitHub Actions가 `정해진 명령을 안전하게 실행하는 문제`였다면 Agentic Workflow는 **판단하는 프로그램을 안전하게 실행하는 문제**가 된다.

따라서 Agent DevOps의 기본 단위도 점점 다음처럼 변한다.

`Agent → Sandbox → Network Policy → Credential Proxy → Safe Output → Human Approval`

Agent를 실제 운영 시스템에 넣으려는 팀이라면 모델 선택보다 먼저 봐야 할 인프라 계층이다.

## 2. `Puffin-World` — 이미지 생성이 아니라 Physics·Geometry·Appearance를 함께 가진 오픈 3D World Model

![Puffin-World](https://opengraph.githubassets.com/1/KangLiao929/Puffin)

### 핵심 요약

9월 3일 공개된 `Puffin-World`는 하나의 Multimodal Model 안에서 **물리 상태, 기하 상태, 시각적 외형**을 함께 모델링해 3D World를 이해·생성·재구성하는 연구다. 단순히 그럴듯한 다음 Frame을 생성하는 Video Model과 달리 중력 방향과 위도, Depth, RGB Appearance를 Native World State로 다룬다.

하나의 초기 View와 Camera Trajectory를 주면 이후 View를 RGB와 Depth로 함께 생성하고, 이를 3D Point Cloud로 재구성할 수 있다. Image-to-3D, Text-to-3D, 자유 시점 생성, 긴 Camera Trajectory, Self-calibrated World Exploration 등을 하나의 Framework 안에서 처리한다.

함께 공개한 `Puffin-16M`은 **15M Vision-Language-Camera Triplet + 1M Camera Trajectory**로 구성되며, 연구팀은 Code·Model·Dataset을 공개했다. 현재 모델은 주로 Static Scene을 대상으로 하며 Physics 표현 역시 중력·Camera Orientation 중심이라는 한계가 있다.

### 왜 중요한가

World Model 경쟁의 목표가 `영상을 잘 만든다`에서 **Agent가 내부적으로 공간과 물리 상태를 유지한다**로 이동하는 신호다.

로봇이나 Embodied Agent가 실제 환경에서 움직이려면 Pixel만 예측해서는 부족하다. `내가 어느 방향을 보고 있는가`, `바닥과 중력 방향은 어디인가`, `물체와 공간의 깊이는 어떤가` 같은 상태가 필요하다.

즉 Multimodal AI의 다음 계층은 다음처럼 발전할 수 있다.

`Image·Video → Spatial State → Physical State → Action → New World State`

Physical AI와 Robotics 쪽에서 주목할 가치가 큰 오픈 연구다.

## 3. Microsoft `Agent Lightning v1.0` — 실제 Agent Harness를 그대로 둔 채 RL로 Agent를 학습

![Agent Lightning](https://opengraph.githubassets.com/1/microsoft/agent-lightning)

### 핵심 요약

Microsoft Research가 최근 공개한 `Agent Lightning v1.0`은 약 **3,500줄 규모의 경량 오픈소스 Agentic RL Framework**다. 핵심은 Agent를 RL Training Framework 안에 다시 구현하지 않아도 된다는 점이다.

기존 Agent가 LangChain, OpenAI Agents SDK, AutoGen 등에서 Tool·Context·Control Flow를 그대로 사용하고, Agent Lightning의 OpenAI-compatible Proxy를 통해 Model Call을 관찰·학습한다. 즉 실제 Production Harness 자체가 RL Rollout 환경으로 참여한다. Microsoft는 이를 `Harnessed Agentic RL`이라고 부른다.

Microsoft의 재현 가능한 Coding Agent 실험에서는 약 **6,000개 Training Example**을 사용해 Qwen3.5-9B의 SWE-bench Verified 성능을 **41.8%에서 56.4%로 14.6%p 향상**시켰다. Agent 실행은 Kubernetes Job으로 직접 돌릴 수 있어 외부 Sandbox 서비스에 종속되지 않는 구성도 제공한다.

### 왜 중요한가

지금까지 Agent 개선은 주로 더 좋은 Foundation Model로 교체하는 방식이었다. Agent Lightning은 다른 방향을 보여준다.

`우리 회사의 실제 Harness + Tool + Workflow + 성공·실패 결과`

를 그대로 학습 데이터로 바꿔 **Agent 자체를 조직의 업무 방식에 맞게 강화학습**할 수 있다.

이 방식이 성숙하면 회사가 축적하는 가장 중요한 AI 자산이 Prompt가 아니라 `실제 Agent Trajectory와 Reward Signal`이 될 수 있다. Agent 운영과 Model Post-training 사이의 경계가 무너지는 흐름이다.

- GitHub: https://github.com/microsoft/agent-lightning

## 4. `OpenClaw 2026.9.2` — 장시간 Agent에서 가장 현실적인 문제인 History·Upgrade·Recovery를 집중 개선

![OpenClaw](https://opengraph.githubassets.com/1/openclaw/openclaw)

### 핵심 요약

OpenClaw의 최신 안정판 `v2026.9.2`가 공개됐다. 이번 릴리스의 핵심은 화려한 새 Tool보다 **장시간 Agent의 상태 유지와 복구 신뢰성**이다.

긴 Transcript와 Disk Usage 처리가 진행되는 동안에도 Chat·Dashboard·Session UI가 막히지 않도록 처리 경로를 분리했고, Dashboard 직접 조회와 Cold-load 감소, Gateway Event Loop 밖에서의 Durable History Read를 추가했다. 자동 Update 시 Active Settings, Enabled Skills, Default Agent Ownership을 보존하고 Git Update 이후 Gateway Restart 복구도 강화했다.

즉 `Agent가 며칠씩 켜져 있을 때` 실제로 생기는 History I/O, State Recovery, Upgrade 실패 같은 운영 문제를 다루는 릴리스다.

### 왜 중요한가

Agent가 짧은 Chatbot일 때는 Model Accuracy가 대부분의 문제였다. 하지만 24시간 동작하는 Personal Agent나 업무 Agent에서는 다른 문제가 커진다.

`Memory 손상 → Session 복구 실패 → Upgrade 후 설정 유실 → Background Task 중단`

같은 문제는 모델을 GPT-6로 바꿔도 해결되지 않는다.

OpenClaw의 최근 릴리스 흐름은 Agent Platform이 점점 **OS나 Server Runtime처럼 상태·복구·업데이트 안정성을 경쟁력으로 갖게 됨**을 보여준다.

## 5. Wistron, `$1.48B` GDS 발행 — AI 서버 수요가 공급망 기업의 자금조달 규모까지 바꾼다

![Wistron AI server plant](https://assets.magica.com/blog/ai-news/2026-07-22/32-wistron-opens-700-million-texas-plant-for-nvidia-ai-server/e8b72c1bd983308e5bd260ccecce941f8ff7c78bb8a3df0102790f605d856309.jpg)

### 핵심 요약

Reuters는 9월 7일 대만 서버 제조사이자 NVIDIA 공급업체인 Wistron이 **최대 $1.48B 규모 Global Depositary Shares 발행**에 나섰다고 보도했다. 조달 자금은 외화 표시 원재료 구매 등에 사용할 계획이다.

배경에는 AI Server 수요 급증이 있다. Wistron은 7월 미국 Texas에 **$700M 규모 공장**을 열어 NVIDIA의 최신 AI System을 생산하기 시작했고, 회사는 Cloud·기업 고객의 AI Server 수요가 여전히 공급을 앞선다고 밝혔다. 2분기 순이익은 전년 동기 대비 **128% 증가**, 매출은 **64% 증가**했다.

### 왜 중요한가

AI Infrastructure Boom이 NVIDIA GPU 가격에만 반영되는 것이 아니다. Server 조립, PCB, 전원·냉각, Memory, Network, 원재료와 공장 증설까지 전체 공급망이 더 많은 Working Capital을 요구한다.

AI 산업의 Capital Stack은 이제 다음처럼 커지고 있다.

`전력 → Data Center → GPU → AI Server → Component Supply Chain → Model → Agent`

Wistron 사례는 AI Capex가 Hyperscaler와 GPU Vendor를 넘어 **제조 공급망 기업의 대규모 Equity Financing까지 밀어 올리고 있음**을 보여준다.

## 이번 회차 핵심

이번 5개를 연결하면 오늘 저녁의 흐름은 **Agent가 똑똑해지는 것보다 Agent를 오래·안전하게·학습 가능하게 운영하는 Stack이 빠르게 성숙하고 있다는 것**이다.

**GitHub Agentic Workflows** → Agent의 Network·Permission·Data Flow 통제  
**Puffin-World** → Pixel을 넘어 Spatial·Physical World State  
**Agent Lightning** → 실제 Harness의 경험을 RL 학습 데이터로 전환  
**OpenClaw** → 장시간 Agent의 State·History·Recovery  
**Wistron** → 이 Stack을 지탱하는 물리적 AI Server 공급망

특히 GitHub Agentic Workflows와 Agent Lightning을 함께 보면 방향이 선명하다. 앞으로 조직의 경쟁력은 `어떤 LLM을 쓰느냐`만이 아니라 **Agent가 어떤 안전장치 안에서 실제 Tool을 사용하고, 그 실행 Trajectory를 어떻게 다시 학습 자산으로 축적하느냐**에 달릴 가능성이 크다.

> **Agent 시대의 핵심 자산은 Model + Harness + Policy + Trajectory + Infrastructure의 결합이다.**
