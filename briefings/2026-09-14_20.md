## 1. ASML High NA EUV 채택 확정 흐름 — TSMC·Samsung·SK hynix가 생산 일정까지 잡기 시작

![ASML TWINSCAN EXE:5200B](https://substackcdn.com/image/fetch/%24s_%210xD9%21%2Cf_auto%2Cq_auto%3Agood%2Cfl_progressive%3Asteep/https%3A%2F%2Fsubstack-post-media.s3.amazonaws.com%2Fpublic%2Fimages%2F25be9a0b-1986-4bd5-a3be-bc7eaad856bf_1410x1064.png)

### 핵심 요약

Reuters가 9월 14일 보도한 내용에 따르면 ASML의 기존 약 2억 달러급 EUV 장비는 사실상 2027년까지 판매 물량이 차 있는 가운데, 약 4억 달러급 차세대 `High NA EUV`에도 주요 반도체 제조사가 구체적인 생산 일정을 잡기 시작했다.

TSMC는 과거 High NA의 경제성을 신중하게 봤지만 이제 2030년부터 첨단 공정 양산에 도입할 계획이다. Samsung과 SK hynix는 2028년부터 메모리 생산에 High NA를 적용할 계획이며, Intel은 이미 High NA 장비로 누적 100만 장 이상의 웨이퍼를 처리했다고 밝혔다.

ASML의 EXE 계열 High NA는 기존 NXE EUV보다 더 작은 패턴을 단일 노광으로 인쇄할 수 있다. ASML 공식 자료 기준 EXE:5200B는 8 nm 해상도와 0.55 NA를 사용하며 기존 NXE 대비 1.7배 더 작은 Feature와 최대 2.9배 높은 트랜지스터 밀도 잠재력을 목표로 한다.

### 왜 중요한지

AI 반도체 경쟁은 GPU Architecture만의 문제가 아니다. 실제로 더 조밀하고 전력 효율적인 GPU·NPU·HBM을 계속 만들려면 Foundry와 Memory 업체가 **차세대 미세공정에 실제 Capex를 집행할 것인지**가 중요하다.

High NA는 수년 동안 `너무 비싼 장비가 아닐까`라는 논쟁이 있었지만, TSMC·Samsung·SK hynix가 생산 시점을 잡기 시작했다는 것은 업계가 2030년대에도 **트랜지스터 Scaling을 AI Compute의 핵심 축으로 본다**는 신호다.

AI Stack을 아래로 내려가면 결국 다음과 연결된다.

`Frontier Model → Accelerator → Foundry·HBM → High NA EUV`

## 2. GitHub `HydraFusion` — Coding Agent가 모델 하나가 아니라 실행 Workflow 자체를 고른다

![GitHub HydraFusion architecture](https://github.blog/wp-content/uploads/2026/09/HydraFusion_architecture_02.png?resize=1024%2C334)

### 핵심 요약

GitHub가 공개한 `Project HydraFusion`은 Copilot CLI의 Research Preview로, 요청마다 단일 모델을 선택하는 수준을 넘어 **여러 모델을 어떤 순서와 역할로 사용할지 Runtime이 결정**한다.

HydraFusion은 현재 세 가지 패턴을 사용한다.

- `Single`: 하나의 모델이 바로 해결
- `Cascade`: 효율적인 모델이 먼저 시도하고 품질 기준을 통과하지 못하면 더 강한 모델로 Escalation
- `Critique`: 한 모델이 초안을 만들고 다른 계열의 독립 Reviewer가 검토한 뒤 최초 모델이 수정

GitHub의 통제된 Offline Benchmark에서 최적 HydraFusion 설정은 Claude Opus 5 대비 TerminalBench 2.1에서 추정 비용을 **67% 낮추면서 검증된 Task 성공률을 4.9%p 높였다**. DeepSWE에서는 비용 36% 감소에 품질 1.5%p 하락, CheckpointBench에서는 비용 65% 감소에 품질 0.1%p 하락이었다. 실제 Production 결과가 아니라 GitHub 자체 평가라는 점은 구분해야 한다.

현재 모든 Copilot Plan에서 Copilot CLI의 `/experimental`을 통해 사용할 수 있다.

### 왜 중요한지

지금까지 Model Router의 핵심 질문은 대체로 `이 요청을 어느 모델에 보낼까`였다. HydraFusion은 한 단계 더 나아가 **이 요청에는 모델 몇 개를 어떤 역할로 연결할까**를 결정한다.

즉 Coding Agent의 경쟁 단위가

`Best Model`

에서

`Best Runtime Workflow = Routing + Cascade + Critic + Revision`

으로 이동하는 흐름이다.

앞으로는 동일한 GPT·Claude·Gemini를 사용할 수 있어도 **어떤 순간에 값싼 모델을 쓰고, 언제 강한 모델로 올리고, 언제 별도의 Critic을 붙이는가**가 비용과 품질을 크게 좌우할 가능성이 높다.

**Sources**  
https://github.blog/ai-and-ml/github-copilot/project-hydrafusion-frontier-quality-via-multi-model-orchestration/  
https://github.com/orgs/community/discussions/206492

## 3. NVIDIA `CUDA Rust` — AI 시스템의 Rust 전환이 GPU Kernel까지 내려온다

![NVIDIA CUDA Rust](https://developer-blogs.nvidia.com/wp-content/uploads/2026/09/image1-1-1024x576.png)

### 핵심 요약

NVIDIA가 9월 8일 Rust로 **GPU Kernel 자체를 작성하고 PTX로 Native Compile**하는 `CUDA Rust` 방향을 공식 공개했다. 단순히 Rust 프로그램에서 CUDA C++ Kernel을 호출하는 Wrapper가 아니라 Kernel을 Rust로 직접 작성하는 것이 핵심이다.

두 개의 오픈소스 경로가 공개됐다.

- `cuda-oxide`: CUDA C++과 비슷한 SIMT 방식. Custom `rustc` Codegen Backend가 Rust MIR → Pliron IR → LLVM IR → PTX로 변환한다.
- `cutile-rs`: Tile 기반 방식. Stable Rust에서 작성하며 CUDA Tile IR을 통해 JIT Compile하고 Thread Mapping과 Memory Layout을 Compiler에 맡긴다.

두 프로젝트 모두 Rust의 Ownership을 활용해 GPU Memory Alias나 일부 Race Condition을 Compile Time에 막는 방향을 취한다. `cutile-rs`는 Stable Rust 1.89+와 CUDA 13.3에서 동작하며 이미 Hugging Face의 Grout Inference Engine과 `mistral.rs`에서 사용되고 있다. 반면 `cuda-oxide`는 Early Alpha이고 NVIDIA도 두 프로젝트 모두 아직 Production-ready는 아니라고 명시한다.

### 왜 중요한지

최근 AI Infrastructure의 하위 계층은 빠르게 Rust로 이동하고 있다. NVIDIA도 Nova Linux Driver와 Dynamo Core 등에 Rust를 사용하지만 지금까지 GPU Kernel은 사실상 별도 언어 영역이었다.

CUDA Rust가 성숙하면

`Agent Runtime → Inference Engine → GPU Kernel`

까지 하나의 Rust 중심 Systems Stack으로 이어질 가능성이 생긴다.

특히 AI Inference 시스템은 극단적인 병렬성과 낮은 Latency를 요구하면서도 Memory Safety 문제가 치명적이다. **성능을 포기하지 않고 시스템 수준의 안전성을 높이려는 Rust의 장점이 GPU Programming까지 확장**된다는 점이 중요하다.

**Sources**  
https://developer.nvidia.com/blog/introducing-cuda-rust-two-tracks-for-writing-gpu-kernels/  
https://github.com/NVlabs/cuda-oxide  
https://github.com/NVlabs/cutile-rs

## 4. AWS SageMaker `PREFIX_AWARE` Routing — KV Cache 위치까지 Cloud Router가 이해하기 시작

![SageMaker intelligent routing and KV cache](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/11/26/ML-19892-1.png)

### 핵심 요약

AWS가 9월 10일 SageMaker Inference에 `PREFIX_AWARE` Routing을 추가했다. 같은 System Prompt, RAG Document, Conversation History, Code File처럼 **동일한 Prefix를 공유하는 요청을 같은 Instance로 보내 KV Cache를 재사용**하게 하는 기능이다.

기존 Random Load Balancing에서는 Prefix Cache를 지원하는 vLLM을 쓰더라도 같은 Context가 매번 다른 GPU Instance로 흩어져 Cache Hit가 낮아질 수 있었다. 새 Routing은 이 Locality를 Endpoint Layer에서 유지하고, Instance가 과부하 상태면 다른 Instance로 넘기는 보호장치도 제공한다. Model Container를 수정할 필요도 없다.

AWS 자체 Benchmark는 Llama 3.1 70B, vLLM, 7대의 `ml.p5.48xlarge` 환경에서 진행됐다. 8,000 Token의 Shared Prefix Workload에서 P50 TTFT가 **71～77% 감소**, P90 TTFT는 **33～37% 감소**, KV Cache Hit Rate는 약 **25% → 82%**, Throughput은 **15～16% 증가**했다. Routing 자체의 추가 Overhead는 요청당 1.3～1.9 ms였다.

### 왜 중요한지

Agent와 RAG 서비스는 같은 긴 Context를 반복해서 읽는다. 따라서 LLM Serving 비용은 Model FLOPS만으로 결정되지 않고 **어디에 어떤 KV Cache가 남아 있는가**에도 크게 좌우된다.

이번 변화는 Load Balancer가 단순히 `어느 서버가 덜 바쁜가`만 보는 것이 아니라 **LLM Context Locality를 이해하는 계층**으로 진화하고 있음을 보여준다.

향후 Agent Infrastructure에서는

`Model Routing + Request Routing + KV Cache Placement`

가 하나의 최적화 문제로 합쳐질 가능성이 높다.

**Source**  
https://aws.amazon.com/blogs/machine-learning/reduce-llm-latency-with-prefix-aware-routing-on-amazon-sagemaker-inference/

## 5. 🔥 GitHub `Strix` — 6.2만 Stars, AI Pentesting Agent가 CI/CD 안으로 들어온다

![Strix](https://github.com/usestrix/.github/raw/main/imgs/cover.png)

### 핵심 요약

오픈소스 AI Penetration Testing 프로젝트 `usestrix/strix`는 9월 14일 확인 시점 **62,333 Stars, 6,826 Forks**를 기록하고 있으며 저장소도 최근까지 활발히 업데이트되고 있다. Python 기반 Apache 2.0 프로젝트다.

Strix는 단순 Vulnerability Scanner가 아니라 Agent가 실제 Pentester처럼 Reconnaissance, Exploitation, Validation을 수행하고 **실제로 재현되는 Proof-of-Concept가 있는 취약점만 남기는 것**을 목표로 한다. 여러 Specialized Agent가 Recon, Exploitation, Post-exploitation을 나눠 수행하는 Multi-agent 구조를 사용하며 Auto-fix, Patch 생성, Retest, Report도 지원한다.

최근 README에서는 GitHub Actions와 CI/CD Pipeline 통합을 전면에 내세우고 있다. Claude Code, Cursor, Codex 등 `SKILL.md` 호환 Coding Agent에서도 `npx skills add usestrix/strix`로 9개의 Pentesting·Fix·CI Skill을 설치할 수 있다. Web·API·Code·OWASP Top 10 테스트를 Agent Workflow에 직접 넣는 방향이다.

공격 기능을 포함하는 도구인 만큼 **자신이 소유하거나 명시적으로 허가받은 Target에서만 사용해야 한다.**

### 왜 중요한지

Coding Agent가 코드 생산량을 크게 늘리면 기존의 `개발 후 보안 Scanner 실행` 방식은 속도 차이를 따라가기 어렵다. Strix가 보여주는 방향은 Security 자체도 Agent화하는 것이다.

`Coding Agent → Pull Request → Pentest Agent → 실제 Exploit Validation → Auto-fix → Retest`

즉 DevSecOps의 자동화 단위가 Static Rule 검사에서 **행동하는 보안 Agent**로 이동하고 있다.

앞으로 Software Team에서 Coding Agent가 일반화될수록, 이를 검증하는 **Security Agent와 Review Agent가 쌍으로 배치되는 구조**가 자연스러워질 가능성이 높다.

## 이번 회차의 핵심

이번 다섯 소식은 AI Stack이 위아래 양쪽에서 동시에 구조적으로 변하고 있다는 점에서 연결된다.

**ASML High NA EUV** → 더 강한 AI Chip을 위한 Physical Manufacturing Scaling  
**GitHub HydraFusion** → 모델 하나가 아니라 Multi-model Workflow를 선택하는 Runtime  
**CUDA Rust** → AI Systems Software와 GPU Kernel의 Rust화  
**SageMaker Prefix-aware Routing** → KV Cache까지 고려하는 LLM Infrastructure  
**Strix** → Software Security Workflow 자체의 Agent화

특히 `HydraFusion + SageMaker PREFIX_AWARE` 조합이 의미하는 바가 크다. 위에서는 **어떤 모델 조합을 사용할지**, 아래에서는 **그 요청을 어느 GPU로 보낼지**를 Runtime이 자동 최적화한다.

결국 AI 서비스의 경쟁력은 `가장 좋은 모델 하나`보다 점점 다음 전체 경로에서 결정되고 있다.

`Task → Agent Workflow → Model Selection → Inference Routing → GPU Cache → Semiconductor Manufacturing`

**한 단계씩 내려갈수록 새로운 최적화 계층이 생기고 있으며, AI 산업의 진짜 경쟁 단위가 Model에서 End-to-end System으로 확장되고 있다.**
